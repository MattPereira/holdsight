# Cache the JWKS response at the CDN

MCP token verification is stateless, but it resolves the signing keys by fetching `/api/auth/jwks` over HTTP, and better-auth trusts a fetched key set for only five minutes. Serving that endpoint reads the `jwks` table, so an agent polling `/api/mcp` on any interval under five minutes wakes the Neon compute at almost exactly the cadence of its five-minute scale-to-zero timer — which consumed most of a month's free-tier CU allowance while the site was otherwise idle. The key set is public and, since better-auth only creates a key when the table is empty, effectively static, so `/api/auth/jwks` now sets `s-maxage=3600` and the CDN answers those refetches instead of Postgres.

The cost is that rotating the signing key no longer takes effect immediately: for up to an hour, verification can fetch a cached key set that lacks the new `kid`, and better-auth's refetch-on-`kid`-miss will be served the same stale copy. Rotation therefore requires purging the CDN cache or waiting out the TTL. Cache headers on an authentication endpoint look like a mistake at a glance; they are deliberate, and the response carries no `Set-Cookie` and no per-user data.
